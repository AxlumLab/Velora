## WinUI 2.3 完整兼容与控件移植执行原则（2026-11-09）

用户明确要求完整覆盖 WinUI 2.3，并移植其控件逻辑代码。目标包括控件属性/事件语义、布局、模板、资源、视觉状态、输入、焦点、辅助功能与生命周期；不能仅用 Gallery 截图或同名类验收。沿用普通 C++23 对象模型，不恢复旧对象 ABI；既有 C++/WinRT 源码和二进制直接兼容不属于已承诺能力。

移植方式按用户最新确认：将 WinUI 2.3 的 C++ 控件行为、模板与资源直接内化到 `modules/fluent/`，成为 Velora 自身实现；`controls` 收敛通用底座。允许破坏性改造，不构建上游运行时，不把整仓镜像纳入产品源码。来源锁定提交 `2237b09d9ba6052414ddccf3d61316de20564303`，MIT、原文件哈希和改写差异见 `modules/fluent/PORTING.md`。不能关闭未知 XAML 诊断来接受模板。

WinUI 2 依赖 UWP XAML。锁定的 2.3 源码中可用的控件逻辑应保留算法和行为、适配至 Velora；其依赖的系统控件和平台能力需要逐项核实来源，以契约、参考程序和回归测试补齐，不能假设整个底层框架都包含在控件源码仓库中。参考：[WinUI 2](https://learn.microsoft.com/en-us/windows/apps/winui/winui2/)、[2.3 发布说明](https://learn.microsoft.com/en-us/windows/uwp/get-started/winui2/release-notes/winui-2.3)。

## 1. 收敛普通 C++ 控件模型

范围：UIElement、BuiltinElements、ElementFactory、Framework、ElementTree、DependencyObject。

先用一个内建控件和一个源码自定义控件验证布局、输入、绘制扩展。保留现有树和属性存储，逐步将集中在 Framework 的控件专属行为移到对应类；Framework 保留树/页面协调职责。公开常用属性和事件的直观 C++ 接口，布局保持 virtual，输入/绘制增加明确扩展点。

完成条件：同一属性从 C++、Binding、样式、XAML 修改时结果一致；自定义控件改变期望尺寸、处理键盘/指针并绘制；挂载/移除、焦点、事件解除和 UI 线程销毁可验证。没有第二份影子状态，没有生成投影。保留现有回归。

## 2. 开放统一元数据与 XAML 加载

范围：reflect、RuntimeTypeRegistry、ElementSchema、XamlIRBuilder、XamlLoader 适配。

定义可组合的类型、属性、事件、内容及模板声明。先让一个源码控件通过正常编译管线被识别和创建，再支持插件元数据目录。声明文件包含稳定名称/ID与语义，不包含进程函数地址。运行期将声明与实际 C++ 工厂/访问器关联。

完成条件：无需向封闭 ElementKind 表硬塞插件枚举即可使用扩展控件；错误可定位；注册事务失败无残留；新无关类型不使旧页面失效。二进制格式升级保留明确兼容规则，不删除 schema 校验来“修好”加载。

## 3. 打通 Android 最小应用

此步暂缓，待 Windows 框架完善后重新安排；不阻塞当前 Windows 控件模型与元数据工作。

范围：NDK/CMake 集成、应用/窗口生命周期、平台服务和 graphics/text 后端。锁定 Impeller 提交及编译选项，先证明可独立嵌入。

第一条纵向路径为：应用启动 → surface → 同一 XAML 页面 → 文本与控件绘制 → 触摸/软键盘 → 页面卸载 → surface 重建。平台服务至少覆盖调度、DPI/逻辑坐标、输入与捕获、焦点、IME、剪贴板、字体/文本测量、包资源、前后台和辅助功能接入点。不要重做全部 WinRT API。

完成条件：真机可输入中英文，旋转/前后台/surface 丢失后可恢复，无重复运行时和无界资源增长。Impeller 负责渲染，文本 shaping、fallback、编辑与语义仍需框架明确负责。Linux 核心测试不计作 Android 验收。

## 4. 交付最小动态插件 SDK

范围：共享库构建、导出/安装配置、插件清单和加载器、元数据/资源事务、C++ 工厂。详细契约见 PLUGIN-SDK.md。

先实现同 SDK 构建严格匹配，Windows DLL 与 Android 同包 `.so` 使用相同声明。宿主与插件链接同一运行时。先成功加载一个具备布局、输入、绘制的 Meter 控件，禁止一开始实现任意版本兼容或热卸载。

完成条件：宿主无需重新链接即可用新控件的动态 XAML；不匹配在调用 C++ 工厂前被拒绝；重复/失败注册回滚；控件关闭无订阅残留；插件在退出前保持驻留。源码静态形态与动态形态行为一致。

## 5. 按历史清单补全 Gallery

固定 WinUI 2.3 参考提交与来源声明，建立页面/控件/属性/状态/交互清单。优先基础控件、文本编辑、焦点/导航、滚动/列表虚拟化，再做复合控件与主题效果。

每一项须有真实样例和行为验证，覆盖模板、资源、键盘/触摸、DPI、主题、辅助功能与销毁。不接入实际树的类、空页面和无作用按钮不能计入。两平台差异记录为明确平台约束，不静默降级。目标是清单完整，不以现有基础 Gallery 代替。

## 6. 确立裁剪与性能预算

开发期间持续测量，此步形成可复现基准及发布配置。建立空窗口、典型表单、长列表、动画、图片/文字等固定负载。

Windows 对比等价 UWP 应用；Android 固定机型、系统、刷新率和热状态。区分工作集/私有内存、CPU/GPU、冷/热启动、帧耗时分布和包体。静态配置证明移除未选模块及专属资源，共享配置验证一份运行时。不要用任意小 MB 数字或只看平均 FPS 作为成功标准。

## 7. 交付 XAML 文本预览器

范围：编辑器、编译诊断、独立预览宿主、文件监视和重建页面。可在第 2 步后先做内建控件预览原型，完整插件体验依赖第 4 步。

完成条件：修改值/资源/模板后实际页面重建；错误保留上一个有效预览且定位到源；生成连接契约、x:Bind 或 C++ 变更明确要求原生重编；插件更新重启预览进程；失败重载无对象和订阅残留。首版不做拖拽设计器或原生代码热替换。
